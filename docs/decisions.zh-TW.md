# 決策記錄（ADR 日誌）

需求說明（brief）留下解釋空間的每一個地方，都連同背景脈絡、所採取的決策，以及
理由記錄在此。貫穿全篇套用的原則：**當規格模糊不清時，採取能讓核心迴圈保持
誠實的最簡單行為，並把它寫下來。**

---

## ADR-001 — patch 引擎內部的定位慣例

**背景脈絡。** hunk 結構儲存的是 1 起始（1-based）的 `old_start`（來自 `@@`），
報告必然是 1 起始（因為要呈現給人類與模型看），但檔案是從 0 開始索引的
`std::vector<std::string>`。第一版實作把兩者混在一起：搜尋產生的是 1 起始的
錨點，而拼接（splice）卻把它當成 0 起始的位移量使用。

**決策。** 搜尋路徑**從頭到尾都是 0 起始**：候選位置 `pos` 代表該簽章會佔用
檔案索引 `[pos, pos + size)`。轉換成 1 起始只發生一次，就是在建立 `HunkReport`
時（`pos + 1`）。此慣例記錄在 `src/patch.cpp` 中「Candidate evaluation」一節的
開頭。

**理由。** 這能防止的錯誤既隱蔽又嚴重：一個漂移的 hunk 會改寫它所匹配的那一行
*上方*的那一行。Golden case 1–60 現在涵蓋了足夠的漂移與空白變異，因此未來任何
慣例上的疏忽都會明顯地失敗。

## ADR-002 — 正規化 hunk 分數

**背景脈絡。** 需求說明指定了

```
score(p) = (0.6*exact + 0.3*fuzzy - 0.2*mismatch) / signature.size()
```

以及 `gate = 0.8`，還有示範輸出會在 exact hunk 上印出 `score 1.00`。這三者無法
同時成立：對一個完美的 hunk（`exact == size`）而言，該公式得出 `0.6`，因此
**每一個** hunk 都會過不了自己的 gate，示範輸出也就永遠無法達成。

**決策。** 改為除以可達到的最高原始分數，而不是除以行數：

```
maximum  = 0.6 * signature.size()
score(p) = (0.6*exact + 0.3*fuzzy - 0.2*mismatch) / maximum
```

完美的 hunk 得分為 `1.00`，`fuzzy_line_threshold` 與 `gate` 維持文件記載的
預設值 `0.8` 與 `0.8`，且示範逐字稿與需求說明相符。

**理由。** 三個限制中有兩個可以原封不動地保留（權重與 gate）；只有分母被修正，
而且是往讓文件記載的門檻具有意義的方向修正。另一種做法——保留字面上的公式並
把 gate 降到 `0.48`——會讓「exact」與「大致錯誤」在回報的分數中無法區分。

## ADR-003 — 編碼 mock 刻意造成的行漂移

**背景脈絡。** 需求說明要求 mock 宣告的 `@@` 位置刻意偏差一行，讓每次示範都會
走到 fuzzy 路徑。對 *replacement* hunk 而言，編碼方式很明顯（declared = true +
1）。對 *pure insertion* 而言，引擎會把 `old_start` 解讀為「把新行放在這個 1
起始行之前」，這與同一個 `+1` 相互作用。

**決策。** Replacement hunk 宣告 `true_position + 1`。唯一的插入規則（補上缺少的
`#include`）宣告 `last_include_line + 2`，在引擎的錨點運算之後，會緊接在最後一個
既有的 `#include` *之後*插入。兩者都實作於 `src/mock_llm.cpp`，並由
`agent_mock.test` 鎖定。

**理由。** 其用意是「模型的猜測差了一行」，而不是「模型產生了壞掉的 patch」，
而引擎的插入語意是對 unified-diff 格式最單純的解讀。

## ADR-004 — 預設不使用 TLS；OpenSSL 須自行啟用

**背景脈絡。** 需求說明只允許四個相依項目，其他一律禁止。`cpp-httplib` 的 HTTPS
支援需要 OpenSSL，而它並不在這四個之內。

**決策。** `FIXIT_ENABLE_OPENSSL` 預設為 `OFF`：純 `http://` 的 OpenAI 相容端點
（Ollama、vLLM、llama.cpp server、測試替身）開箱即可使用。加上
`-DFIXIT_ENABLE_OPENSSL=ON` 後，建置會連結系統的 OpenSSL，`https://` 端點也能
運作。`fixit::openai_tls_available()` 會回報目前生效的是哪一種建置，而以
`--llm openai` 搭配 `https://` URL 時會以離開碼 `2` 和可據以行動的訊息失敗，
而不是令人困惑的傳輸錯誤。

**理由。** 這讓相依清單與規格完全一致，同時讓常見的「本機模型伺服器」路徑
維持完整可用，而且絕不會默默假裝 TLS 存在。

**備註。** 內附（vendored）的 `third_party/cpp-httplib/httplib.h` 帶有一個小小的
本地修補（以註解標示）：上游在 `CPPHTTPLIB_OPENSSL_SUPPORT` 防護之外就 include
了 `<openssl/*.h>`，而且 `#ifdef` 會把 `-D...=0` 視為已啟用。兩者都已正規化，
因此 `FIXIT_ENABLE_OPENSSL=OFF` 真的代表關閉。

## ADR-005 — API key 的處理

**背景脈絡。** 需求說明要求金鑰只能來自 `--api-key` 或 `FIXIT_API_KEY`，且絕不
可被記錄或寫死。

**決策。** 金鑰只存在於 `OpenAiLlm`。`--trace` 絕不記錄它（trace 包含工具呼叫與
觀察結果，而分派迴圈只記錄工具的*名稱*），metrics 寫入器看不到它，傳輸錯誤也只
印出 HTTP 狀態與伺服器的 `error.message`。整棵原始碼樹中不存在任何預設或佔位
金鑰。

**理由。** 提交進版控的 trace 中若外洩金鑰，是本專案唯一無法挽回的錯誤。

## ADR-006 — 相依項目：內附快照*與*固定版號的 FetchContent

**背景脈絡。** 需求說明允許 git submodule 或 `FetchContent`。Submodule 需要 CI
能存取的遠端；`FetchContent` 需要在 configure 時有網路，無法離線建置。

**決策。** 兩者並用。`third_party/` 存放固定版號的原始碼快照（預設路徑；完全
離線且可重現），而 `cmake/ThirdParty.cmake` 會在缺少某個元件時退回使用相同 tag
的 `FetchContent`——沒有快照的全新 `git clone` 仍可完成 configure，而
`-DFIXIT_FETCH_DEPS=ON` 會強制走下載路徑。

固定的修訂版本：

| 元件 | 快照與 FetchContent 固定版號 | 備註 |
|---|---|---|
| tree-sitter runtime | 0.28.0，以 commit `752c612a` 固定 | 0.28.0 尚未發佈（最新的 tag 是 v0.27.0）；快照宣告的就是該版本而 master 與之相符，因此無法用 tag 來識別它 |
| tree-sitter-cpp | v0.23.4 | 語法 ABI 15 |
| nlohmann/json | v3.12.0 | |
| cpp-httplib | v0.59.0 | 快照帶有一個本地修補（見 ADR-027） |
| Catch2 | v3.16.0 | |

固定版號與快照必須一起更新。它們曾經脫節——快照裡是 cpp-httplib 0.59.0 與
Catch2 3.16.0，而這些行仍寫著 v0.28.0 與 v3.8.1——這意味著離線路徑與
`FetchContent` 路徑會建出*不同*的函式庫，而且內附的 cpp-httplib 經過修補，
所以不同的上游修訂版本甚至可能無法編譯。兩條路徑後來都已建置並執行過。

**理由。** 驗收標準是「從全新的 clone 一個指令完成」，而快照不會被上游的
force-push 或在錯誤時刻發生的網路中斷打壞。若快照被移除，備援路徑仍能讓 repo
保持可用。

**備註。** 內附的第三方原始碼絕不使用本專案的 `-Wall -Wextra -Werror` 編譯：
它們是各自獨立的 target 並使用 `SYSTEM` include，因此上游的警告不會弄壞我們的
建置，我們的警告也不會被掩蓋。

## ADR-007 — Clang 的 JSON 方言要用探測的，絕不假設

**背景脈絡。** 需求說明指定使用 `-fjson-diagnostics`。盲目傳入文件所載旗標的
建置會默默失去所有診斷資訊——對一個以編譯器輸出為基準真相的工具而言，這是最糟
的失敗模式。

本 ADR 最初聲稱 Apple clang 17 *想要* `-fdiagnostics-format=json`。在開發所用的
機器上實測，clang 17 會**兩者都**拒絕：`-fjson-diagnostics` 是未知的引數，而
`-fdiagnostics-format=json` 會以 `invalid value 'json'` 失敗。這正是為什麼該旗標
要用探測的，而不是依編譯器名稱來挑選，而 README 是對的，這一段才是錯的。

**決策。** `Compiler` 會對所設定的編譯器探測一次（用一個空的翻譯單元），優先
嘗試 `-fjson-diagnostics`，其次是 `-fdiagnostics-format=json`，最後退回文字
剖析器。強制使用 `Text` 也會阻止已探測出的 JSON 旗標被送出：在剖析文字時傳入
JSON 旗標，會讓一次失敗的編譯產生零筆診斷，看起來就像是乾淨的檔案。只有
`uses_json` 能決定是否送出該旗標。選定的方言會在 `Compiler` 的生命週期內被
快取；`CompilerConfig::format` 可以強制使用 `Text` 或 `Json`。
`parse_diagnostics()` 有對外公開，因此 fixture 可以測試兩種方言而不必啟動
行程。

**理由。** 規格中的旗標會優先嘗試，因此支援它的 clang 行為與文件所述完全一致；
其餘情況則降級為可運作的狀態，而不是無聲的狀態。

## ADR-008 — 編譯器輸出的擷取與逾時

**背景脈絡。** 診斷清單必須具決定性，且不得拋出例外。

**決策。** 使用 `fork`/`exec`，把 `stdout` 與 `stderr` 合併到同一個 pipe，在
`poll` 下以非阻塞方式讀取並設有截止時間。逾時時子行程會被 `SIGKILL`，pipe 被
排空，`timed_out = true` 且 `exit_code = -1`；部分輸出仍會被剖析並回傳。`exec`
失敗時會把 `fixit: cannot execute '<name>': …` 寫進同一個 pipe，因此缺少編譯器
會以一般輸出加上離開碼 `127` 的形式浮現，而不是拋出例外。診斷會依
`(file, line, col, message)` 排序、去重，並上限為 50 筆。GCC 的 note 會被丟棄
（它們無法獨立採取行動）；clang 的 note 則以 `message: note` 併入其母訊息。

**理由。** 修復迴圈必須能在不當掉的情況下說出「編譯器本身沒有執行」，而且相同
的輸入必須永遠產生相同的清單。

## ADR-009 — CodeMap 的具體細節

**背景脈絡。** `enclosing_function(line, col)`、`signature` 與
`context_snippet()` 留下了未定的細節。

**決策。**
* `signature` 是從定義開頭到 body 節點之前那個位元組為止的原始碼文字，並去掉
  尾端空白——因此它絕不包含 `{`（這與需求說明相符，也讓該文字可以直接引用）。
* `enclosing_function` 回傳包含該位置的**最緊密**範圍。`col` 有被接受但未使用：
  在只有一個翻譯單元且沒有巨集展開的情況下，沒有任何位置會因欄而改變答案。
  行內定義（`Widget() = default;`）也算作函式，因為 tree-sitter 會把它們剖析為
  `function_definition`。
* `context_snippet` 會印出 `%4d | %s`，並被夾在 `1..EOF` 之間；它絕不會輸出
  超出檔案結尾的行。
* 檔案缺少、為空或無法剖析都不算錯誤：map 會回報沒有任何函式，且
  `has_syntax_errors() == true`。沒有任何 CodeMap 方法會拋出例外。

**理由。** 這個 snippet 格式正是模型會回引到 patch 中的內容，而對一個在迴圈中
執行的工具來說，「降級、但不拋例外」是必要條件。

## ADR-010 — MockLlm 規則的細節

**背景脈絡。** 需求說明固定了 R1–R4 以及符號→標頭檔對照表，但沒有規定規則如何
與 clang 的錯誤復原互動，也沒有規定當某個符號的標頭檔已經可以遞迴取得時會怎樣。

**決策。**
* **每一輪最多只觸發一條規則，而且它會把它找到的所有缺少標頭檔一次批次處理。**
  在第二個 hunk 上方新增一行，會在同一個 diff 內改變該 hunk 的位置；每次呼叫
  只做一次編輯也是真實模型的行為。
* **只有當沒有任何真正的 `#include` 行提供該標頭檔時，才算「缺少」。** 像
  `std::vector<std::string> words;` 這樣的用法含有字面上的 `<vector>`，絕不可
  被誤認為既有的 include。
* **R1 也會匹配 clang 的 `no member named 'X' in namespace 'std'`**，對這條
  規則而言，那與 `was not declared` 是同一種失敗模式。
* **規則所讀取的檔案，會對照 `patch` 工具使用的同一個 workdir 來解析**
  （`WorkspaceAware`）；由 agent 注入它，因此呼叫方不可能不慎讓兩者分歧。
* **規則表就是需求說明中的表，未作更動。** 某個標準函式庫以遞迴方式曝露的符號
  （libc++ 的 `<string>` 會拉進 `<cstdio>`，所以 `FILE`/`printf` 不需 include
  就能解析）仍然會被加上它的標頭檔——這是無害的編輯，在 libstdc++ 上也同樣
  正確。因此 `e1` 使用的是真正缺少的 `std::vector`，讓 include 規則是被*實際
  演練*，而不只是被執行。

**理由。** 這些是能讓示範保持誠實的最小選擇：規則所提出的修復，必須正是編譯器
實際要求的修復。

## ADR-011 — agent 每一輪都會把編譯器輸出回饋進去

**背景脈絡。** 需求說明說工具結果會以觀察結果的形式附加。它沒有明確指出 patch
之後的*重新編譯*也是一種觀察結果。

**決策。** 在第 *N* 輪的工具執行完之後，agent 會進行編譯，把結果以
`compile_after` 記錄到 trace 中，並在第 *N+1* 輪開始前將它附加為一則訊息。
因此模型絕不會根據過期的錯誤清單來改進。

**理由。** 少了這一點，迴圈會默默修復它在第 1 次迭代看到的錯誤——連行號等等全都
在內——而這正是本專案存在要消除的那一類錯誤。它是由端對端測試發現的，不是靠
人工檢視，現在已由 `agent_mock.test` 涵蓋。

## ADR-012 — 「iterations」是什麼意思

**背景脈絡。** 迴圈會在第一次呼叫模型前編譯一次，每一輪編譯一次，最後再編譯
一次以驗證。示範把最後那次乾淨的編譯也算作一次迭代。

**決策。** `AgentResult::iterations` 計數的是**模型輪數**，等於 trace 陣列的
長度（第 1..N 輪）。最終的驗證編譯會以 `Event::verification == true` 傳遞給
觀察者；CLI 會將它印成結果行（`✓ clean`），而不會另外開啟新的
`── iteration ──` 標題。

**理由。** 一個數字、一種意義，且可對照 trace 檢查。示範仍會顯示那次乾淨的
編譯，這正是讓逐字稿具有說服力的原因。

## ADR-013 — Golden patch 語料庫與 fixture 的來源

**背景脈絡。** 需要 60 個 golden patch 加上 20 個編譯器 fixture；這台機器只有
Apple clang 17（在 macOS 上 `g++` 是指向 clang 的符號連結）。

**決策。**
* 60 個正向與 10 個反向的 patch 案例是由 `tools/gen_golden_cases.py` *產生*，
  並以 `tests/patch_golden_cases.inc` 提交，因此 C++ 測試套件沒有 Python
  相依，但語料庫仍可重現。
* 語料庫刻意包含一個有兩個相似函式的基底檔案，這抓到了一類真實的錯誤：與錯誤
  函式相符的歧義 diff。所有案例都會明確區辨自己的目標。
* 在這台機器上錄製的編譯器 fixture 是 clang 的真實輸出。GCC fixture 則是依
  GCC 文件記載的格式撰寫，並標記為 `"recorded": "synthetic"`；
  `tools/record_compiler_fixtures.sh` 可在有真實 GCC 的機器上重新錄製它們，並
  **拒絕用 clang 輸出覆寫 GCC fixture**。GCC fixture 絕不藉由複製 clang 輸出
  來偽造。

**理由。** 誠實的來源勝過看起來合理的檔案。CI（有 gcc 12）才是真正演練 GCC
方言的環境，而該腳本把這件事變成一個指令就能更新。

## ADR-014 — 平台與建置政策

**背景脈絡。** 在 gcc 12 與 clang 15 上，`-Wall -Wextra -Werror` 是硬性關卡。

**決策。** 這些旗標套用於 `fixit`、`fixit-cli` 及每個測試 target，但絕不套用於
第三方程式碼（各自獨立的 target、`SYSTEM` include）。對我們的程式碼而言警告即
錯誤；上游的警告則視而不見。使用 C++20、`CMAKE_CXX_EXTENSIONS OFF`，以及單一
的 `enable_testing()`/`ctest` 進入點。Windows 不在範圍內，因此直接使用
`fork`/`exec`，而非可攜式的行程包裝層。

**理由。** 對別人的程式碼套用 `-Werror`，會讓建置成為上游發版的俘虜；對我們
自己的程式碼套用 `-Werror` 才是重點。

## ADR-015 — `--metrics` 的格式

**背景脈絡。** 需求說明固定了 JSON 的鍵，但沒有固定各值的意義。

**決策。** `patch_success` 依結果計數 hunk（狀態為 `Applied` 時記為 `exact`，
`FuzzyApplied` 記為 `drift`，失敗則依其結構化原因分類為
`whitespace`/`missing_ctx`）。`fix_rate` 對整次執行而言是 `1.0`/`0.0`，
`avg_iterations` 是該次執行的迭代次數，`total_time_ms` 是牆鐘時間，也是*唯一*
刻意不具決定性的欄位——它永遠不會是 trace 的一部分。

**理由。** Wiki 的成功率章節需要穩定的計數，而把時鐘排除在 trace 之外，正是
讓決定性測試具有意義的關鍵。

## ADR-016 — 有效性數字是如何產生的

**背景脈絡。** W3 里程碑要求一份成功率矩陣與一張熱圖。手工製作的圖表將無法被
否證。

**決策。** `tools/matrix.cpp` 建立語料庫、diff 與執行，並印出表格以及
`docs/patch_success_matrix.json`；`tools/render_heatmap.py` 把該 JSON 渲染成
三張無相依的 SVG。此工具產生的每個 diff 都是*格式良好*的（`@@` 的計數等於實際
引用的行數）；損傷一律在 context 的內容或形狀上，絕不在標頭算術上，因為格式
錯誤的標頭是另一種且無趣的失敗。只有當 hunk 成功套用**且**修復後的那一行真的
取代了預定的那一行時，才算一次成功的試驗：落在錯誤行上的修復算是一次失手。

**理由。** README 與 Wiki 中的數字必須讓任何擁有此 repo 的人都能重現，而且不能
美化引擎。實測結果——在真實的語料庫上，漂移到 ±20 行仍有 100%，而當每個候選都
逐位元組相同時，超過 ±2 就降至 0%——才是這項技術誠實的樣貌。

**對窗梯（window ladder）的後果。** 在一個窗內得到滿分不再結束搜尋：當多個
位置同樣匹配時，該 hunk 屬於最接近宣告位置的那一個，而繼續擴大範圍仍可能找到
更近的候選。一旦存在完美的候選，就會跳過整檔案的備援搜尋，因此常見情況仍保持
低廉。這正是規格中「追蹤全域最佳並以距離作為平手判準」的意圖，如今被明確寫出。

## ADR-017 — 「Clean」要求編譯器真的執行過

**背景脈絡。** `CompileResult::clean()` 原本是「沒有 error 層級的診斷」。無法被
執行（`fork`/`exec` 失敗、離開碼 `127`）或因逾時被殺掉的編譯器會產生*完全沒有
診斷*，因此看起來是乾淨的。`clean()` 是這個迴圈唯一的基準真相，這使得「工具鏈
不存在」與「程式碼已修好」變得無法區分——對這個工具而言是最糟的混淆。

**決策。** 只有當行程以 `0` 結束**且**沒有剖析到 error 層級的診斷時，`clean()`
才為 true。非零的離開碼、逾時或訊號，一律回報為不乾淨。為了仍讓診斷保持可見，
`exit_code`、`timed_out` 與 `raw_output` 一律會被填入，而 `compile` 工具會在
回傳 `clean` 的同時一併回傳它們。

**後果。** mock 模型會偵測到「不乾淨、零錯誤」並以附帶說明的 `FINAL` 回應，
而不是亂猜或陷入迴圈，因此損壞的環境會在一輪內大聲失敗。`agent_mock.test`
涵蓋了這一點，包括原始檔保持原封不動，以及 trace 記錄了 `exit_code: 127`。

## ADR-018 — 標準工具使用迴圈所用的編譯器

**背景脈絡。** `make_standard_tools(workdir)` 建構其 `compile` 工具時使用的是
預設建構的 `Compiler`，也就是 `g++`，不論 `--compiler` 為何。agent 自己的驗證
則使用所設定的編譯器。使用 mock 後端時，這種不一致是看不見的（mock 從不呼叫
`compile`），但任何透過該工具重新檢查自己成果的真實模型，所得到的診斷會來自
與迴圈實際依據的不同編譯器——模型可能「修好」了某個 agent 仍視為壞掉的東西，
反之亦然。

**決策。** `make_standard_tools(workdir, compiler)` 接受編譯器；單一引數的多載
版本為了方便而保留，並使用文件記載的預設值。CLI 與每個測試都把同一個編譯器
物件同時傳給工具與 agent，因此兩者絕不可能不一致。

**理由。** 一個迴圈，一個編譯器。這個錯誤是直接演練工具時發現的（一個刻意不
存在的編譯器執行檔證明了該覆寫被忽略），而不是靠閱讀程式碼發現的。

## ADR-019 — 示範逐字稿可逐位元組重現

**背景脈絡。** §10 要求把示範證據提交進版控，但摘要行會印出牆鐘時間，因此
`docs/demo_output.txt` 每次重新產生都會變動，讀者也無法分辨真正的行為改變與
只是機器較慢。

**決策。** `--no-timing` 會省略經過的時間，而 `tools/record_demo.sh` 使用它。
逐字稿現在每次執行都逐位元組相同（以雜湊兩次驗證過），因此可以作為永不漂移的
證據提交。牆鐘時間預設仍可使用，而且仍然是 `--metrics` 中*唯一*刻意不具決定性
的欄位。

**理由。** 決定性是明訂的品質關卡；每次執行都會變動的產物不算證據。
`expected_artifacts.test` 會檢查提交的檔案中沒有任何時間數值，且提及全部三個
範例。

## ADR-020 — CodeMap 可從 agent 與 CLI 取用

**背景脈絡。** `CodeMap` 原本是只有 CLI 的詳細 context 行及其自身測試會用到的
函式庫類別。迴圈中的模型無從詢問「這個檔案長什麼樣子？」——它只能讀取帶行號的
內容並猜測結構。

**決策。** 兩項新增式的整合，兩者都不改變文件記載的形狀：

* `read` 工具保留其契約（帶行號的 `{content}`），並新增一個選用的 `outline`
  （預設開啟），內容包含函式及其行範圍、include，以及語法錯誤的行。
  `outline: false` 會回傳最小化的答案。
* `fixit <file> --outline` 為人類印出同一份 map 後結束。

**理由。** 需求說明定義了三個工具，因此不新增第四個工具；結構資訊搭著模型本來
就會做的 read 一起帶出。這也讓 `--outline` 有了自然的 CI 用途：它能在不執行
編譯器的情況下，對語法損壞的程式樹明顯地失敗。

## ADR-021 — CLI 的契約透過執行檔來測試

**背景脈絡。** 每個函式庫模組都有測試，但沒有東西檢查使用者實際接觸到的接線：
離開碼、引數處理，以及為可重現性新增的兩個旗標。第一次煙霧測試就立刻發現，
把*目錄*當成原始檔傳入會以 `0` 結束並印出「clean」——一個假綠的建置。

**決策。** `cli_contract.test` 用 `popen` 執行建置出來的執行檔，並斷言可觀察的
契約：用法錯誤（包括目錄會被拒絕並顯示用法文字）、compile 模式的 `0`/`1`、
`--outline` 的內容、`--no-write` 使原始檔逐位元組不變、`--no-timing` 不產生
牆鐘數值，以及沒有金鑰的 `--llm openai` 會以 `2` 結束。用法錯誤現在會把用法
文字印到 stderr；`--help` 仍會印到 stdout 並以 `0` 結束。

**理由。** 函式庫可以完全正確，而執行檔仍然誤報成功，而「exit 0」正是 CI 機器
人唯一信任的輸出。

## ADR-022 — 未知的工具呼叫在 trace 中看得見，且金鑰由測試把關

**背景脈絡。** 有兩種失敗模式沒有留下證據軌跡。如果模型要求一個此建置未提供的
工具，唯一的痕跡就是觀察結果裡的錯誤字串——在診斷卡住的迴圈時很容易漏掉。
而 §10 中的 API key 規則只是政策聲明，背後沒有任何測試。

**決策。**
* 對於 registry 不認識的工具，其觀察結果會帶有 `"unknown_tool": true` 以及
  實際存在之工具的清單，因此 trace 能回答「它要求了什麼，而當時有哪些可用？」。
* `agent_mock.test` 在 `FIXIT_API_KEY` 中植入一個可辨識的金鑰，執行真正的迴圈，
  並斷言該值不會出現在任何 trace、任何 `PatchResult`、任何失敗摘要及任何 CLI
  輸出中。`cli_contract.test` 涵蓋沒有金鑰時 `--llm openai` 的用法錯誤路徑。

**理由。** 只在文字中聲明、未被斷言檢查的品質關卡不算關卡。這兩者檢查起來都很
便宜，而在正式環境中發現的代價卻很昂貴。

## ADR-023 — 跨編譯器一致性是以行、而非欄來斷言

**背景脈絡。** §6 要求一個一致性測試，證明 `e1`–`e3` 在 GCC 與 clang 下產生相同
的 `(line, col)` 集合。這台機器沒有真正的 GCC，因此 GCC fixture 是手寫的，
輕易就能通過。撰寫*實際執行*的一致性測試（用兩者編譯、比較剖析後的輸出）暴露
了缺陷：這兩個編譯器在欄上確實不一致。對 `e3_type_error.cpp` 的
`count_words(value)`，clang 把無效的轉換標在識別字上（`13:15`），而 GCC 指向
引數運算式（`13:25`）。因此，嚴格的 `(line, col)` 斷言會與它本欲驗證的那些工具
相衝突，而且只可能在合成資料上通過。

**決策。** 兩個一致性案例都精確斷言錯誤的**行**集合，並且只比較欄是否可用
（每個回報的欄必須為 `> 0`）；欄的差異會透過 `INFO` 呈現，而不是讓測試失敗。
此分歧及其成因記錄在 `tests/fixtures/compiler/README.md`。個別 fixture 仍會
斷言自己精確的行、欄，因此剖析器本身仍被緊緊鎖定。

**理由。** 行才是真正重要的契約：它決定了修復迴圈所依據的 hunk context。斷言
超出工具所能保證的內容，會讓 CI 因為一個並非 FixIt 缺陷的原因而失敗，而默默
放寬則會掩蓋真正的剖析器退化——因此才有明確的 `INFO` 以及每個 fixture 各自的
欄斷言。

## ADR-024 — `-ferror-limit` 要用探測的，因為 GCC 沒有這個旗標

**背景脈絡。** §3.1 指定了固定的旗標組合
`-std=c++20 -fsyntax-only -ferror-limit=<N>`。這對 clang 成立，對 GCC 則不成立：
`g++-12` 會回答

```
g++-12: error: unrecognized command-line option '-ferror-limit=5'
```

並且在編譯任何東西之前就結束。結果是*零筆診斷*，這與乾淨的建置無法區分——
因此在 ubuntu/gcc-12 的 CI 工作中，每次編譯看起來都成功，但其實什麼都沒被
編譯。整個測試套件在 macOS 上是綠的，因為那裡的 `/usr/bin/g++` 是 clang。

**決策。** 能力探測從診斷方言延伸到選用旗標。只有在編譯器接受時才會傳入
`-ferror-limit=N`；否則就省略它（內部的 50 筆診斷上限仍然適用）。這需要移除
一個早期的 `return`，它會對任何名稱看起來不像 clang 的編譯器完全跳過探測——
這也是為什麼即使第一次嘗試修正之後，該旗標仍被傳給 GCC。探測本身也必須從
「以 0 結束且輸出可剖析的 JSON」改為「編譯器是否*拒絕*這個旗標？」，因為
`-ferror-limit` 會被默默接受且不輸出任何東西。

**後果（已接受的偏離）。** 使用 GCC 時，`error_limit` 無法被遵守：GCC 沒有提供
等效的旗標，因此它會回報每一個錯誤，而不是前 N 個。FixIt 自身 50 筆已剖析診斷
的上限仍然適用。這件事在此記錄下來而非加以模擬，因為藉由截斷輸出來發明一個
上限，會藏起編譯器認為相關的診斷。

**如何發現與驗證。** CI 工作的日誌給出了確切的拒絕訊息；接著用一個 GCC 行為
模擬器（拒絕該旗標但輸出 GCC 格式的診斷）在本機重現了它。對照該模擬器，三個
範例的行為完全符合要求：e1 與 e2 以 0 結束，e3 以 1 結束，而修復後的 e1 可以
編譯。保留 CI 工作——而不是信任本機工具鏈——才是讓這件事浮現的原因；Linux 上
第一次全綠的執行就是證明。

## ADR-025 — 跨編譯器一致性斷言的是有問題的陳述式，而不是錯誤集合

**背景脈絡。** §6 要求一個 gcc/clang 一致性測試，證明 `(line, col)` 集合完全
相同。對真實的 GCC 執行後顯示，這不是任何兩個編譯器都具備的性質。對
`e1_missing_include.cpp` 而言，同一個缺少的分號會讓 GCC 發出 **10** 筆診斷，
而 clang 發出 **5** 筆，因為它們的錯誤復原不同；完整的行集合也不同
（{10, 14, 20, 21} 對 {10, 14}）。欄也同樣不同（e3 上 `13:25` 對 `13:15`）。
因此，相等性的斷言只可能在手寫的 fixture 上通過，而 CI 第一次使用真正的 GCC
時它就失敗了。

**決策。** 兩個一致性案例都斷言真正被保證、且對修復迴圈真正重要的東西：

* 每個編譯器都至少回報一個錯誤，且兩者都沒有漏掉該缺失；
* 兩者各自的**第一筆**診斷都指向同一行（那一行就是選出 hunk context 的依據）；
* clang 標記的每一行，GCC 也都標記了——GCC 可以再往上連鎖更多，但不能少；
* 欄必須可用（`> 0`），但不進行比較。

個別 fixture 仍會斷言自己精確的行、欄、層級與訊息，因此剖析器仍被緊緊鎖定；
只有跨編譯器的比較被放寬，而分歧會被量測並透過 `INFO` 印出。

**後果。** 封存的語料庫保留手工對齊的 GCC fixture。它們標記為
`"recorded": "synthetic"`，並可在有真實 GCC 的機器上用
`tools/record_compiler_fixtures.sh` 重新錄製。因為一致性斷言不再比較數量，
重新錄製它們不會弄壞測試套件。

## ADR-026 — `tools/gcc_sim.py` 之所以存在，是因為這台機器沒有 GCC

**背景脈絡。** 開發是在 macOS 上進行，那裡的 `/usr/bin/g++` 是 clang。有兩個
GCC 專屬的缺陷在任何人能在本機看到之前就進到了 CI：只有 clang 才有的
`-ferror-limit` 旗標，以及真實 GCC 無法滿足的一致性斷言。每一個都耗掉一次 CI
來回與一次翻日誌。

**決策。** 提供一個小型的 GCC 替身（`tools/gcc_sim.py`），它會像 g++-12 一樣
拒絕只有 clang 才有的旗標，並輸出 GCC 形狀的診斷，只把 clang 當作其分析後端。
它可以被符號連結為 `PATH` 上的 `g++`，本機測試套件於是能重現 CI 的狀況：有了
它，完整測試套件 6/6 通過，而在 ADR-024 修正之前，它失敗的方式與 CI 完全一樣。

**理由。** 這個模擬器誠實地表明自己是模擬器（診斷是真的，驅動程式不是），它
不屬於建置的一部分，也不取代 CI：ubuntu/gcc-12 的工作仍然是真實 GCC 的權威。
它把回饋迴圈從一次 CI 來回縮短到幾秒鐘，而這正是上述兩次失敗實際耗費的成本。

## ADR-027 — TLS 須自行啟用，且其信任儲存區是明確指定的

**背景脈絡。** 需求說明只允許四個相依項目，而 OpenSSL 不在其中，因此在預設
建置中無法使用 `https://`。因此，擁有自己的 API key、卻使用 `https://` 端點的
使用者，若不自行啟用就無法使用這個工具。啟用之後又浮現了兩個必須處理、而不能
只用文件帶過的 macOS 現實：

1. cpp-httplib 在 Apple 平台上會從 Keychain 載入信任儲存區，這需要
   `CoreFoundation` 與 `Security`。在 `INTERFACE` 連結中以純字串傳遞
   `"-framework X"` 無法留存到最終的執行檔，符號會遺失，因此這些 framework
   改用 `find_library()` 解析，並附加到實際進行連結的 target 上。
2. 系統的 OpenSSL 不會讀取 Keychain（那是 SecureTransport 的特權，這也是系統
   `curl` 能運作的原因），因此憑證驗證對一張有效的 Let's Encrypt 憑證失敗了。
   Keychain 開關也必須正規化，因為內附的 httplib 是用 `#ifdef` 來測試它，
   `-D...=0` 因此仍然會啟用它。

**決策。** `FIXIT_ENABLE_OPENSSL=ON` 提供 TLS，並由
`FIXIT_MACOS_KEYCHAIN_CERTS`（預設 `ON`）在 Keychain 與 CA bundle 之間作選擇。
兩種情況下 `OpenAiLlm` 都會明確地把 OpenSSL 指向一個 bundle：若有設定
`$FIXIT_CA_BUNDLE` 則用它，否則在 macOS 上用 `/etc/ssl/cert.pem`，再否則用
Linux 常見的路徑，而且只在該檔案存在時才用。憑證驗證絕不會被停用。兩種建置
風味都能通過完整測試套件。

**理由。** 「SSL 驗證失敗」是使用者能拿到最無法據以行動的錯誤，而默默停用驗證
會更糟。把信任儲存區明確化，既維持四相依的規則（TLS 仍須自行啟用），又讓擁有
金鑰的使用者真正能使用它。

**金鑰處理。** `--api-key`/`FIXIT_API_KEY` 仍是唯一的來源。包裝腳本
`tools/fixit_with_my_key.sh` 讀取值之後，在 exec CLI 之前將它 unset，因此金鑰
不會出現在 `argv` 中，也無法進到 trace 或 metrics 檔案；有一項測試會斷言植入
的金鑰不會出現在任一處。

## ADR-028 — 一個已追蹤的缺陷：插入型 hunk 可能弄丟後面那一行

**背景脈絡。** 用真實模型（透過 OpenAI 相容端點）驅動引擎時，產生了形狀如下的
hunk

```
@@ -7,3 +7,4 @@
 #include <string>
+#include <vector>
 
 int main() {
```

而套用後的結果把插入點之後的那一行刪掉了。原因在套用路徑：它消耗 `old_count`
行檔案內容，卻輸出 `context + additions` 行新內容。當一個 hunk 既引用 context
又新增一行時，這兩個數量會相差新增的行數，因此拼接會晚了一行才接續。

這件事**不是**由 golden 語料庫發現的。每個 golden 案例插入一行時都*沒有*引用其
前後的 context，或者是取代而非插入，因此它們都沒有以真實模型的方式，把
「引用的 context」與「新增的一行」結合起來。

**決策（第一輪）。** 把它記錄下來，而不是再推出第三個推測性的修正。有兩次嘗試
被回退：第一次讓測試套件發生 segfault，第二次讓 60 個案例的 golden 語料庫保持
全綠，卻在其他地方弄壞了，因為把標頭宣告的數量與 hunk 實際引用的行數調和，
會改變*每一個* hunk 的替換範圍計算。因此它是由一個標記為 `[!mayfail]` 的測試
重現（明顯失敗，但無法讓 CI 變紅），並在此連同其確切輸入記錄下來。

那個標記已不存在：下一節記錄了修正，而該測試現在是一個會通過的普通
`[patch][regression]` 案例。比這個缺陷活得更久的教訓是關於語料庫，而不是程式
碼——每個產生的案例都是*取代*行，因此沒有任何一個把引用的 context 與插入的一行
結合起來，而真實模型實際產生的形狀就這樣沒被測到。

在同一次修正中也補上了一個相關的缺口：剖析出零個 hunk 的 diff 以前會回傳一份
沒有任何說明的空報告，而這正是真實模型最常遇到的失敗（它的 `@@` 標頭不符合
預期的形狀）。`patch` 工具現在會回傳原因，加上所收到 diff 的前 600 個位元組，
而在實際測試時，模型在下一輪就修正了它的格式。

**解決方式。** 已在同一系列中修正。套用路徑現在把它先前混為一談的兩個數量分開：

* 消耗的跨度是 **hunk 所引用的舊側行數**——context 加上刪除的行——只會朝著標頭
  中*更大*的 `old_count` 放寬（這正是標頭存在要救援的情況：模型省略了 context）；
* 寫出的內容是引用的 context（取自檔案，因此未被更動的程式碼保留自己的位元
  組）、新增的行，以及任何被放寬的 context。

純刪除（`@@ -2,1 +2,0 @@`，一行 `-` 且沒有 `+` 行）會移除它的行且不寫入任何
東西，而先前的形狀在相反方向上弄錯了這件事。共修正了三個錯誤，且每一個都有
涵蓋：刪除的情況、「放寬得太急躁」的情況，以及當新側沒有引用任何內容時的越界
讀取。

為測試語料庫記錄下來的教訓：全部 60 個產生的案例都是取代行，因此沒有任何一個
把引用的 context 與插入的一行結合起來。針對該形狀的回歸測試現在已經存在。

## ADR-029 — 編譯器旗標是直接傳遞，不是猜測出來的

**背景脈絡。** `CompilerConfig` 一直都有 `extra_flags` 欄位，但 CLI 從未填入它。
因此任何 include 了專案標頭檔的檔案都會以 `'math_utils.h' file not found` 失敗，
FixIt 根本看不到真正的診斷，這使得該工具除了自成一體的檔案之外都無法使用。

**決策。** 新增 `-I DIR` / `--include DIR`、`-D NAME[=VALUE]` 以及通用的
`--flag FLAG`，全部都可重複，全部原樣轉送；併寫的 `-Iinclude` 形式也可接受。
回顯的指令行會包含這些旗標，讓使用者能確切看到實際執行了什麼。

**已否決的替代方案。** 自動剖析 `compile_commands.json` 會更方便，但那是第二種
輸入格式，有自己的失敗模式，而且需求說明並未要求。從程式樹猜測 include 路徑則
比兩者都更糟：無聲的錯誤路徑會產生錯誤的診斷，比缺少旗標更難察覺。明確的旗標
能保有一個真實來源。

**後果。** 現在要除錯一個真實的檔案是：

    fixit src/parser.cpp -Iinclude --agent --llm openai ...

其中的 `-I` 與專案原本使用的相符。
