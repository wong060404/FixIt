# Wiki outline (W3)

A one-page structure for the project Wiki. Each section says what goes there and
which artefact in this repository supplies it — everything is already generated
by the tools, so the Wiki is a matter of pasting, not re-measuring.

---

## 1. Motivation — why "the patch did not apply" is the bottleneck

**Lead with the failure, not the feature.** A model writes a correct edit, the
`@@` header is two lines stale, `patch(1)` refuses the whole diff, and the model
never learns why. Three concrete artefacts:

* the `PatchEngine::failure_summary()` example from the README §6.3 — the text a
  model actually receives;
* `docs/demo_output.txt` iteration 2, where a hunk declares `L11` and lands on
  `L10` (`fuzzy, drift-1`) and the repair still completes;
* the honest counter-example: the identical-block column of
  `docs/patch_success_heatmap_ambiguous.svg`, where the engine *cannot* choose.

## 2. Demo — GIF / video

Record with `tools/record_demo.sh` running live (the script writes the text
transcript; capture the terminal for the GIF). 60–90 seconds:

1. `fixit e1_missing_include.cpp --agent --llm mock --verbose` → exit 0.

3. `fixit e3_type_error.cpp --agent --llm mock --verbose` → exit 1, reported honestly.
4. `ctest --test-dir build --output-on-failure` → `100% tests passed`.

Drop the GIF at the top of the page. The text version of the same transcript is
`docs/demo_output.txt`, regenerated by the same script.

## 3. Effectiveness — the patch success-rate matrix

**Image 1 (main result):** `docs/patch_success_heatmap.svg`
4 impairments × 7 drift distances, 200 trials per cell, well-formed diffs.
Mean apply rate 100%, worst cell 99%.

**Image 2 (stress test):** `docs/patch_success_heatmap_shared_context.svg`
Boilerplate that repeats (`}`, blank lines, near-identical function bodies) with
one unique line to repair: still 100% up to ±20 lines of drift.

**Image 3 (the limit):** `docs/patch_success_heatmap_ambiguous.svg`
Every block byte-identical. Below ±2 lines of drift it is 100%; at ±5 and beyond
it is 0%, because the declared position is the *only* information that could
disambiguate and it is wrong. This is the honest boundary of the technique.

Numbers and method: `docs/patch_success_matrix.json`, produced by
`./build/bin/fixit-matrix`. Regenerate both with:

```bash
./build/bin/fixit-matrix docs/patch_success_matrix.json
python3 tools/render_heatmap.py            # writes the three SVGs
```

The heat maps are plain SVG (no plotting dependency), so they render in the Wiki
and diff sensibly in git.

## 4. Trajectory — what the loop actually did

Screenshot or paste `examples/buggy/expected/e1_missing_include.trajectory.json`:

```json
{
  "compiler": "clang++", "exit_code": 0, "success": true, "iterations": 2,
  "initial_errors": 5, "final_errors": 0,
  "rounds": [
    {"round": 1, "tool_calls": ["patch"], "errors_before": 5, "errors_after": 1},
    {"round": 2, "tool_calls": ["patch"], "errors_before": 1, "errors_after": 0}
  ]
}
```

`errors_before` is what the model was shown; `errors_after` is what the compiler
said once it acted. The full trace (per-round `compile_before`, `compile_after`,
tool calls and observations) is what `--trace` writes.

## 5. Architecture and code pointers

Reuse the README's ASCII diagram (§5) and link the four headers:
`include/fixit/{compiler,codemap,patch,agent}.h`. Call out the two design rules
that make the loop trustworthy:

* the compiler is the only ground truth (a `FINAL` answer still triggers a
  recompile);
* every failure is structured (`score`, gate, closest position, offending line,
  suggested re-read) instead of an exit code.

## 6. Engineering notes worth a paragraph each

* `-Wall -Wextra -Werror` on our code, never on third-party code (ADR-014).
* The dialect probe: Apple clang 17 rejects both JSON flags, so the parser
  degrades to text instead of losing diagnostics (ADR-007).
* The scoring normalisation that made `gate = 0.8` reachable (ADR-002).
* The 0-based position convention that killed a drifted-hunk rewrite bug (ADR-001).
